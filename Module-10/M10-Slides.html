Module 10① Ask nicely
① Ask nicelyWhat to do00-warm-up/ask_it_nicely.py

Stop asking. Check.

The instruction and the attack arrive through the same channel, in the same format, with the same authority. The model has nothing to tell them apart with.

  1. Put a canary in the system prompt — a unique marker, here ORCHID-7742. If it ever appears in output, your instructions leaked.
  2. Write code_check(reply) — four lines. If the canary is in the reply, return a safe substitute instead of the reply.
  3. Call it on every reply, between the model and the customer. Not inside the prompt. Not as a request. In code, on the way out.
The warm-up makes the LLM calls once and scores the same replies twice — so the only thing that changes between round 2 and round 3 is those four lines.

Module 10② The door
② The doorWhat to doex1-the-door/desk_solution.py

Ask one dull question: is this even a message?

  1. Write check_input(text) returning (ok, cleaned, reason) — one function, called before anything else.
  2. Reject empty, and reject anything longer than MAX_CHARS (4,000 — a customer message, generously).
  3. Strip the structure markers in CONTROL_TOKENS: ###, <<, {{, [INST]. They mean something to a prompt and nothing to a customer.
  4. Call it first in handle(case), and return before the model is ever invoked — that is where the saving comes from.
What must NOT go in it: a list of scary phrases. A customer writing "please ignore my previous email, I found the parcel" is a customer. Cap length, strip structure, never guess intent.

Module 10③ The fence
③ The fenceWhat to doex1-the-door/desk_solution.py

Mark everything you did not write

To a language model there is no structural difference between "your instructions" and "text you were given".

  1. Write fence(label, content). Wrap the content in a delimiter whose name ends in secrets.token_hex(4) — a nonce the attacker cannot guess. A fixed delimiter like ``` is guessable, and guessable means closeable.
  2. Inside the fence, say plainly that the contents are data from a database, typed by a human, and that instructions found inside it must never be followed.
  3. Call it from orders_mentioned(text) — every retrieved record, tool result, document or other agent's reply goes through it.
  4. Do not strip the markers out of retrieved content. You clean the door; you fence the data. Stripping destroys evidence.

Module 10④ Least privilege
④ Least privilegeWhat to doex2-the-hands/hands_solution.py

Delete the capability

Does a desk that answers "where is my order" need to send mail to an arbitrary address?
  1. Keep one tuple, EXPOSED_TOOLS, and remove email_customer from it. That is the whole change.
  2. Build the tool list you send the model from that tuple — policy.schemas_for(EXPOSED_TOOLS) — never hard-code it, or the two drift apart.
  3. Leave the tool's validation rule in shared/policy.py anyway. Two cheap layers, so the day somebody re-exposes it you are still covered.
No prompt to write, no check to maintain, and no bypass — a capability that was never handed over cannot be abused. Half of real hardening is deleting something.
Real-world shape. A Chevrolet dealer's chatbot was talked into "agreeing" to sell an SUV for $1 in December 2023. The bug was not its prompt — it was that a sales chatbot had authority to make commitments.

Module 10⑤ The allow-list
⑤ The allow-listWhat to doex2-the-hands/hands_solution.py

Let the model pick the row. Never the value.

  1. Write check_call(name, args) and call it on every tool call the model proposes, before anything runs.
  2. Check the name against EXPOSED_TOOLS first. This is what catches a tool that does not exist.
  3. Check every argument. Does the order exist? Is the amount a number at all? Is it under policy.TOOLS["issue_refund"]["max_amount"]?
  4. Then the line that matters most: does the amount equal the order's own recorded amount? Compare against get_order(order_id)["amount"]. The model may choose which order. It may not choose how much.
  5. End with fail closed: a tool with no validation rule is refused, not allowed. That covers your next typo.
And keep the refusal boring. What you send back to the model says "not permitted, do not state amounts or limits" — because an early version fed the real reason back and the desk told the customer "$4,999.00 exceeds our policy limits". Your refusal message is an oracle.

Module 10⑥ The gate
⑥ The gateWhat to doshared/policy.py + hands_solution.py

Gate few enough things that they still get read

  1. Classify every tool in shared/policy.py — config, not code, which the model cannot read or change. Each gets a risk, a needs_approval and a why.
  2. Write ask_human(name, args, mode) and make its first line if not policy.needs_approval(name): return True. Safe tools must never prompt.
  3. Default policy.needs_approval to True for a tool it has never heard of — fail closed, including on your own typos.
  4. Show the human what they need: the tool, the arguments, the amount, and why it reached them. Default to no: [y/N], and only the exact string "y" approves, so a stray Enter denies.
Prefer undo over approve. A reversible action with a 30-second undo needs no human in the loop at all, and is still recoverable.

Module 10⑦ The mouth
⑦ The mouthWhat to doex1-the-door/desk_solution.py

Block what must never be seen. Redact what must not be repeated.

Write check_output(reply) and call it on every reply before the customer sees it. Four checks, and the order is the craft.

  1. Empty → send a safe substitute, not a blank.
  2. The canary. If CANARY is in the reply, block — and explain nothing. An error message is a hint.
  3. The egress allow-list. For every address EMAIL_RE finds, if its domain is not in ALLOWED_DOMAINS, block the whole reply. The domain is the payload — masking the local part is not enough.
  4. PII → CARD_RE.subn(...) to redact, not block. The customer still deserves their answer.
  5. Last, the format contract: truncate past MAX_REPLY_CHARS.
Real-world shape. DPD's bot swore at a customer (Jan 2024). Air Canada's invented a refund policy and a tribunal held the airline to it (2024). And across several assistants, an injected instruction made the model emit a markdown image whose URL carried your data — the browser does the leaking. The vendors' fix was a URL allow-list. Exactly check 3.

Module 10⑧ The meter
⑧ The meterWhat to doex3-the-meter/meter_solution.py

One control, two optimisations

  1. THE CONTROL. RUN_BUDGET_USD — check meter.dollars() before the call and raise BudgetExceeded. Checking afterwards is an apology, not a control — the same argument the door makes and the gate makes. Fail closed, on cost.
  2. cache_get(key) — exact match with a TTL, and two exclusions that are safety rules: never cache a turn that moved money or opened a gate (a cached refund is a second refund, approved by nobody), and never cache by similarity — that serves customer A's answer to customer B.
  3. pick_model(text) — route in code: order count, length, a word list. Never ask a model which model to use. And notice what you are really deciding: which model reads your most untrusted content.
  4. Re-run the suite and read compare(before, after). It is allowed to tell you the optimisation was worthless.
The bug that bit us: the first router counted order ids with a plain regex. A card number is four groups of four digits — so every customer who mentioned a card looked like a four-order question and got the model costing 2.7× more. Nothing failed. No test went red. Router bugs do not crash; they invoice.

Module 10⑨ The secret door
⑨ The secret doorWhat to doshared/policy.py + secret_door.py

Match shapes and machine-written names. Never sentences.

  1. Put the rules in policy.SECRET_RULES as data — pattern, action, the company policy each satisfies, whether rotation is needed. To add a rule you add a row.
  2. Match by shape (AKIA+16, a PEM header) or by a machine-written name with a value after it (CLIENT_SECRET=…). Never by prose — "I forgot my password" is a customer.
  3. Write secret_door(text): run the named rules first, then the entropy backstop for formats nobody wrote a rule for — skipping everything in NOT_SECRET_SHAPES (UUIDs, git SHAs, tracking numbers).
  4. block a live credential; redact the customer's own card. And resolve overlaps by specificity, then length, so the vague rule never outranks the one that can name the thing.
  5. Log the finding, never the value: rule, offset, length, and a one-way fingerprint. Then tell the user to rotate it anyway — it was on their clipboard regardless of what you did.

Which guardrail do I need?

  1. Can it do something irreversible? → an approval gate, on that action only. Or make it reversible and skip the gate.
  2. Does it read anything a stranger wrote? → a fence, and assume the fence will sometimes fail.
  3. Is there a value the model should not choose — an amount, a recipient, a row count, a path? → code supplies it.
  4. Could the output disclose something? → the mouth, with an egress allow-list.
  5. Could it loop? → a step cap and a spend ceiling.
  6. Does it hold a tool it has not needed this month? → delete it.
  7. Have you changed the model, the prompt or the tool list since you last measured? → you have not measured.
