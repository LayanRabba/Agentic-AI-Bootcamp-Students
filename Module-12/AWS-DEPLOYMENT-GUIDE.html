1. What we are building

A chat agent with short-term memory (the current conversation, compacted when it grows), long-term memory (facts stored in a vector database and recalled in later sessions) and a visible “Compacting conversation…” notice. It runs as one Docker container on a small EC2 server, and CloudFront puts HTTPS in front of it.

Browser ──https / wss──▶ CloudFront ──http (port 80)──▶ EC2 (Ubuntu + Docker) (free HTTPS cert, │ global edge) ▼ container: uvicorn + FastAPI :8000 ├─ / chat UI (static HTML) ├─ /ws WebSocket chat endpoint ├─ /health health check ├─ short-term memory (RAM, per session) └─ long-term memory (Chroma, on disk) │ ▼ OpenRouter API (the LLM)
AWS pieceWhy we need it
EC2 (t3.micro)Runs the container. A WebSocket needs a long-running server, so Lambda is a poor fit. The app uses about 280 MiB, so 1 GB of RAM is enough.
Security groupThe firewall. We only allow CloudFront to reach port 80.
Elastic IPA fixed address, so CloudFront’s origin does not change if the instance restarts.
CloudFrontGives us https:// / wss:// for free, with no certificate or domain to manage.
S3 (temporary)Delivers the pre-built Docker image to the server without needing a registry, a git repo or SSH.

2. Why WebSockets and streaming?

The problem with plain HTTP

An LLM takes several seconds to write a full answer. With a normal HTTP request the browser would stare at a spinner until the entire reply is ready, then show it all at once. It feels slow even when it isn’t.

Streaming: show the answer as it is produced

LLMs generate text token by token (a token is roughly ¾ of a word). Streaming means we forward each token to the user the moment it exists:

Without streaming
llm.invoke(prompt) waits for everything.
Measured: nothing on screen for ~3.8 s, then the whole answer appears.
With streaming
llm.astream(prompt) yields chunks.
Measured: first words after ~1.8 s, text keeps flowing until done.

Total time is similar, but perceived latency (time to first token) drops a lot. For long answers the difference is dramatic.

Why WebSockets are the right transport here

NeedPlain HTTP request/responseWebSocket
Server pushes many small piecesOne response per requestServer can send any number of messages on one connection
Extra events (compacting, budget, done, error)Awkward: needs custom framingEach message is a JSON event with a type field
Per-session stateNew connection every requestOne connection = one session, so we keep short-term memory per connection
OverheadHeaders and handshake for every messageHandshake once, then tiny frames
Alternatives: Server-Sent Events (SSE) also stream and are simpler, but they are one-way. WebSockets are two-way, which is why the same connection carries both the user’s messages and the agent’s events. They are also the pattern used in the previous modules.

The code

Server side (app.py): the important part is the async for loop that forwards each chunk immediately.

@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()
    session_memory = ShortTermMemory()          # one per connection

    while True:
        data = await websocket.receive_text()   # user message arrives
        ...
        if status.get("compacted"):             # event: tell the UI
            await websocket.send_text(json.dumps(
                {"type": "compacting", "status": "Compacting conversation..."}))

        async for chunk in llm.astream(prompt): # real streaming
            await websocket.send_text(json.dumps(
                {"type": "token", "text": chunk.content}))

        await websocket.send_text(json.dumps({"type": "budget", "data": budget}))
        await websocket.send_text(json.dumps({"type": "done"}))

Browser side (static/index.html): append every token as it arrives.

const proto = location.protocol === 'https:' ? 'wss:' : 'ws:';
const ws = new WebSocket(`${proto}//${location.host}/ws`);

ws.onmessage = (e) => {
  const data = JSON.parse(e.data);
  if (data.type === 'token')      bubble.textContent += data.text;   // streaming
  if (data.type === 'compacting') showCompactingNotice();
  if (data.type === 'budget')     updateDashboard(data.data);
  if (data.type === 'done')       enableInput();
};
Why HTTPS (and wss://) matters: a page served over https:// is not allowed to open an insecure ws:// connection. That is the main reason we put CloudFront in front of EC2: it provides HTTPS, so the browser uses wss:// automatically.

3. Preparing the app with Docker

Docker packages the app and everything it needs (Python version, libraries) into an image, so it runs the same on your laptop and on EC2. All the code is in Module-12/starter-code/.

3.1 Files

starter-code/
├── app.py              FastAPI app: /ws, /health, /memory/stats, /memory/reset, serves the UI
├── memory_manager.py   short-term compaction + long-term Chroma memory
├── static/index.html   chat UI
├── requirements.txt
├── Dockerfile
└── .env.example

3.2 requirements.txt

numpy<2 is essential. chromadb 0.4.24 crashes on import with NumPy 2 (np.float_ was removed), and an unpinned install pulls NumPy 2.

3.3 Dockerfile

FROM python:3.12-slim
WORKDIR /srv

# chroma-hnswlib is compiled during install, so we need a C++ compiler
RUN apt-get update && apt-get install -y --no-install-recommends build-essential \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Pre-download the embedding model so the first chat message is fast
RUN python -c "from chromadb.utils.embedding_functions import DefaultEmbeddingFunction; DefaultEmbeddingFunction()(['warmup'])"

COPY app.py memory_manager.py ./
COPY static/ static/

EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
  • --host 0.0.0.0 is required. With the default 127.0.0.1 the app is unreachable from outside the container.
  • Copying requirements.txt first lets Docker cache the slow install layer when only code changes.
  • The warm-up line bakes the embedding model into the image. Without it, the server would download it during the first chat message (about 7 seconds of silence).

3.4 Build and test locally before you touch AWS

Build the image on your own machine, never on the server. Building on EC2 wastes launch time, needs a bigger (more expensive) instance just for the compiler and pip, and fails in ways you can barely see. A pre-built image makes the server’s job trivial: download, load, run.

cd Module-12/starter-code
cp .env.example .env            # put your OPENROUTER_API_KEY in it

# --platform must match the server CPU. Our EC2 is x86_64 (t3), and a Mac with
# Apple Silicon is arm64, so we ask for linux/amd64 explicitly.
docker buildx build --platform linux/amd64 -t chat-agent:latest --load .

docker run --rm --platform linux/amd64 -p 8000:8000 --env-file .env chat-agent:latest
# open http://localhost:8000
No Docker on a Mac? brew install colima docker docker-buildx, then colima start --vm-type vz --vz-rosetta. Rosetta makes the amd64 build run at near-native speed (about 2 minutes for this app). On an x86 machine or a CI runner just drop --platform. Alternatively pick a Graviton (arm64) instance type such as t4g and build natively on an Apple Silicon Mac.
Rule of thumb: if it does not work on your laptop, it will not work on AWS, and on AWS you can barely see the logs. Every bug we hit during the first deployment attempts (NumPy, missing compiler, wrong LLM client settings) would have been caught by this one step. You can also check the footprint: docker stats showed about 280 MiB of RAM, which is why a 1 GB t3.micro is enough.

3.5 Export the image for delivery

docker save -o chat-agent-image.tar chat-agent:latest     # about 440 MB
The image file has no secrets in it. The API key is passed at run time (-e OPENROUTER_API_KEY=...), never baked in. .dockerignore keeps .env and memory_store out of the image.
Production alternative: push the image to Amazon ECR (docker push) and have the instance docker pull it using an IAM role. We use S3 here so there is no IAM to set up.

4. AWS Console steps

Pick one region and stay in it. We use Europe (Ireland) eu-west-1. Check the region selector in the top-right of the Console before every step. Resources in the wrong region are the most common “it’s missing!” mistake.

Create an S3 bucket and upload the code

  1. Console → S3 → Create bucket.
  2. Name: something globally unique, e.g. m12-chat-agent-<account-id>. Region: eu-west-1. Leave Block all public access ON.
  3. Open the bucket → Upload → select chat-agent-image.tar (about 440 MB, so it takes a minute).
  4. Click the uploaded object → Object actions → Share with a presigned URL → set 2 hours → Create → copy the URL. You will paste it into the user-data script.
The presigned URL lets the server download that one private file without any IAM role. It expires on its own.

Create the security group (firewall)

  1. Console → EC2 → Security Groups → Create security group.
  2. Name module-12-chat-agent, VPC: the default VPC.
  3. Inbound rule: Type Custom TCP, port 80, Source: Prefix list → com.amazonaws.global.cloudfront.origin-facing.
  4. Leave outbound as is (the server needs internet to install Docker and call OpenRouter). Create.
Why not 0.0.0.0/0? Some organizations run governance automation that silently deletes open-to-the-world rules (we saw exactly this: the rule vanished seconds after creating it, and nothing could connect). Restricting to CloudFront’s IP list is also the better design: nobody can bypass CloudFront and hit your server directly. Consequence: http://<server-ip> will not answer. Always use the CloudFront URL.
No port 22 (SSH) on purpose. Students do not need a key pair for this lab; diagnostics come from the console log (see Pitfalls).

Launch the EC2 instance

  1. EC2 → Launch instance. Name: module-12-chat-agent.
  2. AMI: Ubuntu Server 22.04 LTS.
  3. Instance type: t3.micro (1 GB RAM). The image is pre-built, so the server only has to run it (about 280 MiB). It is also free-tier eligible in many accounts.
  4. Key pair: Proceed without a key pair.
  5. Network: default VPC, any subnet, Auto-assign public IP: Enable. Select the existing security group module-12-chat-agent.
  6. Storage: 12 GiB gp3 (room for the image and its extracted layers).
  7. Advanced details → User data: paste the script below, replacing the two placeholders.
#!/bin/bash
exec > >(tee -a /var/log/m12-deploy.log | tee /dev/console) 2>&1
set -x
apt-get update
apt-get install -y docker.io curl
systemctl enable --now docker
curl -fsSL "PASTE_PRESIGNED_URL_HERE" | docker load || { echo M12-LOAD-FAILED; exit 1; }
docker run -d --name chat-agent --restart always -p 80:8000 \
  -e OPENROUTER_API_KEY=PASTE_YOUR_KEY_HERE \
  -e ADMIN_TOKEN=PICK_A_LONG_RANDOM_STRING \
  -e ANONYMIZED_TELEMETRY=False chat-agent:latest
echo M12-DEPLOY-DONE
  • User data runs once, at first boot, as root. It is the “install script” of the server. Notice there is no build step: it just downloads the image, loads it and runs it.
  • tee /dev/console sends the output to the instance’s console log so you can read it later (Pitfalls section).
  • -p 80:8000 maps the server’s port 80 to the container’s 8000.
  • --restart always brings the container back after a reboot.
The API key is visible to anyone who can view the instance’s user data. Fine for a throwaway class demo; rotate the key afterwards. In production use Secrets Manager or SSM Parameter Store with an IAM role.
  1. Click Launch instance. The server is healthy about 90 seconds after launch (Docker install plus image download), versus roughly 4 minutes when we built the image on the server.

Allocate and attach an Elastic IP

  1. EC2 → Elastic IPs → Allocate Elastic IP address → Allocate.
  2. Select it → Actions → Associate Elastic IP address → choose your instance → Associate.
  3. Open the instance details and copy its Public IPv4 DNS, which looks like ec2-54-72-85-236.eu-west-1.compute.amazonaws.com. You need it next.
CloudFront rejects raw IP addresses as an origin; it wants a DNS name. Use the Public IPv4 DNS, not the IP. If that field is empty, the VPC has “DNS hostnames” disabled (enable it under VPC → Actions → Edit VPC settings).

Create the CloudFront distribution

  1. Console → CloudFront → Create distribution.
  2. Origin domain: paste the EC2 Public IPv4 DNS (type it manually if it is not suggested).
  3. Protocol: HTTP only, port 80. (CloudFront ↔ EC2 is plain HTTP; the viewer side is HTTPS.)
  4. Origin response timeout / keep-alive: raise to 60 seconds (under origin settings).
  5. Viewer protocol policy: Redirect HTTP to HTTPS.
  6. Allowed HTTP methods: GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE.
  7. Cache policy: CachingDisabled. Origin request policy: AllViewer.
  8. WAF: do not enable (not needed for the lab). Create distribution.
  9. Wait until the status changes from Deploying to a date (5 to 10 minutes). Your URL is https://dxxxxxxxxxxxxx.cloudfront.net.
Why these settings? CloudFront supports WebSockets out of the box, but it must forward the Upgrade / Sec-WebSocket-* headers (that is what AllViewer does) and it must not cache anything (CachingDisabled), otherwise the chat would be served stale or the upgrade would fail. Idle WebSocket connections are eventually closed by CloudFront; the UI then shows “Disconnected” and you simply refresh the page (a good place for students to add auto-reconnect as an exercise).

5. Testing the deployment

  1. Health: open https://<your-cloudfront-domain>/health. Expect {"status":"ok","service":"chat-agent"}.
  2. UI: open the root URL. The status should show connected.
  3. Streaming: ask “Write a 100-word story about a robot.” The text should appear progressively, not all at once.
  4. Compaction: send 5 or more short messages (e.g. “My dog is called Rex”, “I live in Haifa”…). Around message 5 you should see “Compacting conversation…”.
  5. Long-term memory: tell it “I prefer tea over coffee.”, then refresh the page (a new session, so short-term memory is empty) and ask “What drink do I like?”. It should answer from long-term memory.
  6. Stats: https://<your-cloudfront-domain>/memory/stats shows turn, summary and memory counts.
The first answer is a little slower than later ones (the LLM connection warms up), but the embedding model is already inside the image, so there is no long download.

Resetting long-term memory

Memory lives inside the container, so a reboot does not clear it. To wipe it between demos, call the reset endpoint. It only works if you set ADMIN_TOKEN in the docker run above and send the same value in a header; otherwise it answers 403.

curl -X POST https://<your-cloudfront-domain>/memory/reset \
  -H "X-Admin-Token: PICK_A_LONG_RANDOM_STRING"
# {"status":"reset","removed":3}

Check /memory/stats afterwards: long_term_memories should be 0. Keep the token secret, since anyone who has it can erase the memory.

6. Pitfalls we hit (and how to avoid them)

SymptomCauseFix
Browser: “DNS probe finished”CloudFront domain typed from docs with a placeholder, or the distribution was deleted/never createdCopy the real domain from the CloudFront console
Nothing on port 80, no errorSecurity group has no inbound rule (an automatic governance policy removed 0.0.0.0/0)Allow the CloudFront prefix list instead. Re-open the SG to check the rule is still there.
CloudFront 504 Gateway TimeoutCloudFront cannot reach the origin: container down, SG blocks CloudFront, or the user-data failedCheck the SG, then the console log
CloudFront rejects the originYou entered an IP addressUse the Public IPv4 DNS name
Server never became healthy; log shows M12-LOAD-FAILEDThe presigned URL expired or was pasted wrong (it must be one unbroken line, including every & parameter)Generate a new presigned URL and relaunch
Container exits with exec format errorImage built for the wrong CPU (arm64 image on an x86 server)Build with --platform linux/amd64, or use an arm64 (t4g) instance
Local docker build: pip conflicting dependenciesMixed pins of langchain / langchain-openai / tiktokenUse the pinned requirements.txt above
Local docker build: error compiling chroma-hnswlibOnly gcc installed, g++ missingbuild-essential in the Dockerfile
Container exits at start: np.float_ was removedNumPy 2 with chromadb 0.4.24numpy<2
Chat replies with “Did not find openai_api_key”The LLM client was created without the OpenRouter key and base URLPass api_key and base_url (see app.py)
Instance stops by itself at nightOrganization scheduler (a Schedule tag added automatically)Only in company accounts. Ask the account owner; use a personal or sandbox account for the lab.
Long-term memory stays at 0The app saved the assistant’s reply instead of the user’s messageFixed in this version: store the user message

How to see what the server is doing (no SSH)

EC2 → select the instance → Actions → Monitor and troubleshoot → Get system log. Because the user-data pipes output to the console, you will see the apt, docker build and M12-DEPLOY-DONE lines there. If you see M12-BUILD-FAILED, scroll up for the pip or docker error.

7. Cleanup (do this after the class)

Everything below costs money while it exists (EC2 hours, the Elastic IP, CloudFront requests). Delete in this order:

  1. EC2 → Instances: select the instance → Terminate instance.
  2. EC2 → Elastic IPs: select the IP → Release (after the instance is gone).
  3. CloudFront: select the distribution → Disable, wait until it is deployed, then Delete.
  4. EC2 → Security Groups: delete module-12-chat-agent.
  5. S3: empty the bucket, then delete it.
  6. Rotate or delete the OpenRouter key you put in the user data.

8. Same thing from the CLI (what the instructor ran)

export AWS_REGION=eu-west-1          # and --profile <name> if you use profiles
ACC=$(aws sts get-caller-identity --query Account --output text)
B=m12-chat-agent-$ACC-euw1

# 1. code to S3 + presigned URL
aws s3 mb s3://$B
aws s3 cp chat-agent-image.tar s3://$B/chat-agent-image.tar
URL=$(aws s3 presign s3://$B/chat-agent-image.tar --expires-in 7200)

# 2. security group: CloudFront only
VPC=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query 'Vpcs[0].VpcId' --output text)
SG=$(aws ec2 create-security-group --group-name module-12-chat-agent \
      --description "Module 12" --vpc-id $VPC --query GroupId --output text)
PL=$(aws ec2 describe-managed-prefix-lists \
      --filters Name=prefix-list-name,Values=com.amazonaws.global.cloudfront.origin-facing \
      --query 'PrefixLists[0].PrefixListId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG \
  --ip-permissions "IpProtocol=tcp,FromPort=80,ToPort=80,PrefixListIds=[{PrefixListId=$PL}]"

# 3. instance (user-data file = the script from step 3, with URL and key filled in)
AMI=$(aws ssm get-parameter \
  --name /aws/service/canonical/ubuntu/server/22.04/stable/current/amd64/hvm/ebs-gp2/ami-id \
  --query Parameter.Value --output text)
IID=$(aws ec2 run-instances --image-id $AMI --instance-type t3.micro \
  --security-group-ids $SG --user-data file://user-data.sh \
  --metadata-options HttpTokens=required \
  --block-device-mappings 'DeviceName=/dev/sda1,Ebs={VolumeSize=12}' \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=module-12-chat-agent}]' \
  --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-running --instance-ids $IID

# 4. Elastic IP + DNS name for the CloudFront origin
EIP=$(aws ec2 allocate-address --domain vpc --query AllocationId --output text)
aws ec2 associate-address --instance-id $IID --allocation-id $EIP
aws ec2 describe-instances --instance-ids $IID \
  --query 'Reservations[0].Instances[0].PublicDnsName' --output text

# 5. CloudFront: origin = that DNS name, http-only :80, viewer redirect-to-https,
#    cache policy CachingDisabled, origin request policy AllViewer, all HTTP methods
aws cloudfront create-distribution --distribution-config file://cf.json

# 6. test
curl https://<domain>.cloudfront.net/health
